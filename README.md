# Herald

**One notification broker. Independent products. Android and the web.**

[Protocol](docs/protocol-v1.md) · [Publishing guide](docs/publishing.md) · [Self-hosting](docs/deployment.md) · [Herald Android](https://github.com/Omnific-Tech/herald-android-oss) · [Herald Web](https://github.com/Omnific-Tech/herald-web-oss)

</div>

Herald is a self-hosted notification broker for independent products. Your backend publishes a message; Herald routes it to subscribed devices, retries delivery, and records acknowledgements. Android apps receive notifications through **Firebase Cloud Messaging**; browsers use **Web Push** with per-application VAPID keys.

Your product owns notification content, user preferences, and its application experience. Herald owns delivery. This repository is the product-agnostic broker, with its own database and configuration; no Omnific product backend is required.

## What it handles

- **Multiple applications:** separate product origins, producer credentials, devices, and routing catalogs.
- **Channel and topic routing:** broad channel subscriptions or exact topic matches, managed by each product.
- **Reliable acceptance:** application-scoped idempotency keys prevent duplicate publication when producers retry.
- **Delivery lifecycle:** retries, expiry, acknowledgements, and recorded delivery errors.
- **Operator controls:** an authenticated admin API, an admin UI, and a provisioning CLI.

| Project | Responsibility |

## Quick start

Requires **Docker with Compose** and **Go 1.25 or newer** for the key-generation command. From a checkout:

```sh
cp .env.example .env
go run ./cmd/heraldctl keygen
```

Set the generated value as `ENCRYPTION_KEY` in `.env`, then start the broker:

```sh
docker compose up --build -d --wait
curl --fail http://localhost:8080/health
```

Compose starts PostgreSQL, applies migrations, and serves the broker on localhost port **8080**. Database data persists in a dedicated volume. The example credentials are for local development; configure your own database credentials, HTTPS, allowed origins, and backups for deployment. See [deployment](docs/deployment.md) and [operations](docs/operations.md).

FCM is optional. To deliver Android notifications, configure `FCM_PROJECT_ID` and provide Application Default Credentials for the same Firebase project used by your Android app. The [environment example](.env.example) documents local and optional S3-compatible credential configuration. Web Push uses the encryption key to protect VAPID private keys at rest.

## Connect your product

Provision an application and its producer:

```sh
docker compose exec herald ./heraldctl create-application \
  -slug sample -name 'Sample App' \
  -origin https://app.example.com -subject mailto:ops@example.com
docker compose exec herald ./heraldctl create-producer \
  -application sample -name sample-api
```

Keep returned producer credentials on your backend. Set `CORS_ALLOWED_ORIGINS` to your product's exact origin, configure its Android or web client for this broker and application slug, and create the routing topics you intend to publish to.

Publish through `POST /v1/messages` with the producer's bearer token. Supply a stable `idempotency_key`, a known channel/topic, a trusted same-origin path, and an explicit `expires_at`. The [publishing guide](docs/publishing.md) covers complete request examples, acceptance responses, and producer retry behavior.

For operator access, configure `ADMIN_USERNAME`, an Argon2id `ADMIN_PASSWORD_HASH` generated by `heraldctl hash-password`, and an exact `ADMIN_ORIGIN`. See the [admin API](docs/admin-api.md) and [admin UI](admin/README.md).

## Development and verification

For development outside the app container, start PostgreSQL with `compose.test.yaml`, set `DATABASE_URL` for that database, and run `make run`. See [Contributing](CONTRIBUTING.md) for the complete development checks.

Public CI exercises HTTP/database flows with `make e2e-admin` and `scripts/test-delivery-errors-e2e.sh`, retaining inspectable JSON reports under `artifacts/e2e/`. Database-backed suites require `HERALD_TEST_DATABASE_URL`; checks that omit it skip those scenarios. Android FCM and browser push-service behavior also require client-side verification.

The release workflow builds AMD64 and ARM64 container images under the `herald-oss` namespace with immutable source-commit tags. Production deployment automation and credentials are maintained separately from this repository.
